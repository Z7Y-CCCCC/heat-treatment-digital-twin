# 安装包进一步优化：默认生效且验证真实解压

Ethan 已明确要求合并修复、生成并上传新的安装包，以及进一步优化体积与速度。版本为 2.3.4。之前“只核查、不打包”的阶段已结束；仍禁止读写现场库、替换固定模板或跳过验收。

## 同输入实测

对同一份已验证的 v2.3.3 程序/插件目录逐个压缩，不修改输入。体积为字节，阶段耗时不代表全流程。

| 项目 | 原设置 | 新设置 | 结果 |
|---|---:|---:|---|
| 主程序 7z 容器 | 级别 1：630,310,862 字节 / 51.438 秒 | 级别 2：613,821,366 字节 / 45.224 秒 | 减少 16,489,496 字节（2.62%），该次压缩缩短 12.08% |
| 完整离线插件 ZIP | 级别 3、2 线程：257,013,539 字节 / 14.493 秒 | 级别 3、8 线程：257,013,539 字节 / 3.922 秒 | 大小不变，该次压缩缩短 72.94% |
| 同一组 2,182 个源码输入（492,379,934 字节） | 串行 SHA-256：18.436 秒 | 8 路有界读流：4.844 秒 | 文件集合、每文件摘要和最终摘要完全相同；本项测量期间另有资源测试运行，不把单次比值当作保证 |

两种主程序 7z 均另用安装器实际采用的 **x86 Nsis7z.dll** 解压，不是只运行桌面版 `7za t`。1,694 个文件及空目录完整核对，内容树 SHA-256 均为 `a1599a30b7765c984131801bd49c08497c452ea45dd33fa4f99b3df8e2a48d8f`；解压及两端逐文件核对阶段分别为 26.761 / 23.740 秒。插件归档都通过完整性测试。

## 自动应用的规则

- `desktop/scripts/release-compression-policy.cjs` 是默认压缩策略来源：主容器级别 **2**，不强制 BCJ2；插件 ZIP 仍为级别 **3**，按机器并行度取 1–8 线程。
- `生成安装包.ps1`（双击/`npm --prefix desktop run dist`/GitHub 构建）和安装界面重包入口均读取相同策略。旧安装包的旧压缩级别不会暗中覆盖新默认值。
- 显式 `ELECTRON_BUILDER_COMPRESSION_LEVEL` 覆盖和 FastPack=0 保留；退出后恢复原环境。高压缩仍须通过真实原生解压门禁，不能仅因压缩率好而交付。
- 源码快照命令默认执行 8 路有界 SHA-256，保持原排序和摘要格式。读取前后校验大小、mtime、ctime、inode、设备身份，读取后再次核对完整文件集合；不是 mtime 缓存，不少读源文件。
- 保留此前的非 OneDrive 暂存、受控原生/依赖/前端缓存、移除未用 MeCab 字典、并行首启/重启/迁移与全部完整性检查。

## 防止再次“压缩成功却装不全”

每次生成正式 EXE 后，除实际打开/关闭设置页，还从 **最终 EXE 原字节**取出应用 7z，用同一 x86 NSIS 插件在自有临时目录解压，与本次程序目录逐文件、逐目录、逐 SHA-256 比较。证据绑定最终 EXE、压缩块、解压器及内容树摘要；收集/上传/下载门禁对 2.3.4 起强制检查。缺文件、损坏、摘要不符均停止。

安装现场还会检查主程序、Node、后端、Unity、后台宿主和运行库脚本是否存在；缺少时保留错误/日志并停止，不能展示成功。

上述解压 fixture 不写注册表、不注册服务、不安装运行库、不启动大屏。它与解包后的主程序/采集首次启动、重启、迁移、空业务数据和固定模板检查互补，不能冒称为所有 Windows、提权 SCM 或现场升级全覆盖。最终安装包大小与整轮耗时以本次 `build-timings.json` 和 Release 清单为准。

## 干净 CI 构建补充修复

第一次合并后完整构建在采集验收中被拦截：服务已就绪，但测试网关误读 `frontend/dist`；干净发行前端实际在本次 `win-unpacked/resources/frontend`。现在由发行调度器显式传入这个目录，启动私有数据库前就验证输入完整，禁止回退到开发残留。保留界面 200、采集端不提供界面 404、真实签名测试激活、Cookie/CSRF、首启/重启、采集持续运行和私有 MySQL 退出断言。

同一份失败候选的采集资源已用修正后的测试完成首启/重启，432 个资源文件前后摘要完全一致。此结果只是诊断和回归证据，不拿它跳过下一轮正式构建的任何检查。

同时把两个 Microsoft 离线运行库的缓存移到 `%LOCALAPPDATA%/HeatTreatmentDigitalTwinBuild/runtime-prerequisites-v1`，避免 CI `checkout clean` 和失败重试把缓存删掉、每次重下约 240 MB。旧缓存只在 Microsoft 签名验证后迁入；每次构建仍对自己暂存目录中的实际文件重新验证 Microsoft 签名和完整 SHA-256。缓存只允许这两个公共运行库，不存账户、私钥、现场数据或机器授权。

## 最终 EXE 取件门禁修复

第二轮正式构建的主程序、采集和迁移验收、最终 EXE 设置页启闭均通过，但新增的解压门禁失败：构建工具附带的精简 `7za` 不含 NSIS 解析器，自动探测误认了内嵌插件 ZIP。没有发布该失败构建，也没有改写它的失败记录。

门禁改为从最终 EXE 扫描唯一的 7z 数据块：按官方格式校验签名、版本、StartHeader CRC、NextHeader CRC、长度和文件边界；零个或多个有效块都失败。随后仍用相同 x86 Nsis7z 插件解压，与本次程序目录逐文件和空目录核对。新增回归覆盖 ZIP 干扰、假签名、跨扫描块签名、截断、歧义、CRC 损坏和实际解压缺文件；原生测试在普通子进程中捕获工具日志，避免 Windows Node 测试 IPC 被第三方原始标准输出破坏，不跳过原生测试。

修正后对该 873,453,701 字节候选 EXE 的独立验证通过：1,693 个文件全部一致，包含取件/真实解压/两端散列的门禁耗时 28.777 秒。此记录只证明修复有效；正式发布仍须由新一轮完整工作流通过全部检查，不复用失败状态、不绕过运行测试。
