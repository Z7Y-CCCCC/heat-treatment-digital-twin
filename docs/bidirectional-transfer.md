# 双侧进出料联动

配置入口仍为后台「设备动画联动 → 实时进出料联动」，工位位置沿用「设备运动配置」。不另建平行配置。

## 配置与信号

- 料车使用目标工位、实际移动 BOOL、独立到位工位；估算位置不能解锁交接。
- 循环使用三个来源设备的 BOOL：循环开始、取料模式（true 取料 / false 送料）、车上物料在位。
- 每个目标工位明确指定设备、送料侧、该目标设备自己的只读 BOOL 物料在位反馈、真实承料节点及其本地坐标。
- 本地仿真点位必须标明虚拟来源；现场地址由真实 PLC 表确定，不将仿真地址当成现场反馈。
- `cartHome`、`seatNodeLocal` 为 glTF 模型局部坐标；物料尺寸为米，场景按该产线 `sceneUnitsPerMeter` 换算。Unity 只做一次 X 轴镜像。

启用循环后，`clip:feed`、`clip:hook`、`clip:feed_opposite`、`clip:hook_opposite` 交由循环独占驱动，不得再启用四项独立点位绑定。其余电机、辊道等绑定保持独立。

## 动画与确认

同源 Three.js 派生机构导出两侧的伸链和脱钩动作，Unity 直接采样相同导出轨迹；原始 CAD 文件不改，车体不掉头，也不拉伸推链。为了避免叠加和额外绘制，只显示当前工作的送料侧。

伸链、脱钩、退链、辊道接料的中间姿态均按可配置时长平滑估算，并不是现场行程百分比。送料路径为车上承料面 → 设备口 → 设备内承料节点；取料相反。目标货物随真实承料节点移动，交接中的同一物料只有一份显示。

只有车上与设备内两个独立在位 BOOL 同时满足交接后的状态，才允许完成勾合/脱钩并退链。等待超时保持等待；断线、陈旧值、类型错误、停靠失效或几何不可达冻结过程，不用计时伪造确认。开始信号须先恢复低位才可再次触发。

后台「产线设备联动」加载同一保存配置、动作包和循环规则，默认检查实际显示布局；它仍是使用合成 BOOL 的离线预览，不读写 PLC。Unity 前台才消费实时反馈。这里的“同步”是配置与动画规则一致，不是后台预览在控制现场。

## 几何边界与测试

设备口高度、方向、轨道停靠横向误差和原机构最大位移必须全部满足保存的公差。设备内承料面还须与车上承料面同高，设备口须处于两承料位之间。显示布局标定不等于物理现场测量。

- `node backend/scripts/bidirectional-transfer-test.cjs`：隔离后台正常 HTTP 保存/重开、BOOL 归属、动作唯一所有者与因果边界。
- `npm --prefix frontend test`：双侧动作、共享循环及离线预览回归。
- `dotnet run --project tools/native-runtime-tests`：JS / C# 共用 1280 步循环轨迹和 BOOL 时序、断线、重放边界。
- Unity Windows 构建执行 `BidirectionalTransferValidation`：真实 Transform 与导出动作包两侧半行程、送料、取料、物料唯一性与独立反馈门控检查；不需要 GUI。

回滚应先停用循环，再恢复之前保存的运动、进出料口及显示布局配置；恢复原动作绑定后才能卸载双侧动作包。不要回滚数据库连接、草稿或其他设备点位。
