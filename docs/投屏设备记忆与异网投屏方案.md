# 投屏设备记忆与异网投屏方案

## 本轮实现

- 设备线、小车导轨：尚未保存的新项显示绿色边框和左上角斜向“新增”；保存失败保留标记，保存成功或放弃修改后清除。不往布局数据写临时标记。
- 后台“局域网电视”和用户菜单“投屏”共用同一份设备记录，投过的项绿色描边、优先显示；未发现时仍保留该项，点击“查找并连接”。不把历史记录算作当前可投数量。
- 按电视 UPnP UDN（`uuid:…`）识别，不按名称、IP、MAC 猜测。电脑/电视正常重启、DHCP 改地址后，重新发现并核验 UDN，使用当前地址连接。原 IP 被另一台电视占用时不得向其发送投屏命令。
- 只有接收端实际请求并收到编码流的首个数据块才记为“投过”。这表示视频流开始传输，不能证明电视面板已经解码显示；单纯发送播放命令成功不计入。
- 本机记录：`APP_DATA_DIR/cast-history.json`，未配置 APP_DATA_DIR 时为 `backend/data/cast-history.json`。原子写入、最多 32 项；只存设备 ID、名称、厂商、型号和最后投屏时间，不存旧 IP、控制地址、媒体令牌或账户密码。不同工程、账号共用本机记录，但读取/操作仍受投屏权限控制；不随工程迁移包传给其他电脑。
- 缺少稳定 UDN 的非规范设备仍可当次投屏，但不能可靠跨 IP 识别，因此不伪造“记住”。电视恢复出厂设置或自行重生成 UDN 时要重新识别，不能仅凭同名自动认作原设备。
- 两个顶端标签复用完全相同的选中悬浮样式。

## 顶端栏不进入投屏

当前内置 DLNA 投送的是 Unity 客户区域的编码视频，不是远程桌面。已有两道处理，本轮补回归：

1. 原生宿主进入纯画面模式，隐藏顶部标签和独立标题浮层，数据面板扩展至完整客户区。
2. 纯画面模式不可用时，编码器按实际 DPI 裁掉顶部标签栏（46 / 69 / 92 等物理像素）。已隐藏时不重复裁切。

第三方投屏软件若自行抓整个桌面，本程序**无法保证其排除任何窗口**。优先选择裁剪后的内容区域，不能选择“整个桌面”；如果只选 Unity 窗口，还须确认软件同时捕获 WebView 数据浮层，否则会漏掉组件。将来内置异网投屏也必须只采集纯画面合成区域，不能用整屏捕获再遮住标签伪装。

## 异网投屏：本轮仅方案，未接入公网

### 建议路线

`本机 Unity＋WebView 合成画面 → H.264/WebRTC → ICE 优先直连 → 电视 HTTPS 接收页`

- 电视打开我们的接收网址，显示短时配对码；电脑输入/确认码后建立会话，不需要安装第三方接收软件。
- 小型 HTTPS/WSS 服务负责配对、信令、设备授权和撤销。STUN 协助发现候选路径，能直连则音视频不经过服务器。
- 不可直连时自动 TURN 中继（UDP，必要时 TCP/TLS 443）。没有 TURN，企业防火墙、部分运营商 NAT 场景就无法保证稳定，不能承诺“完全无服务器、任何网络均可”。这是 WebRTC 官方说明的连接方式：[Peer connections](https://webrtc.org/getting-started/peer-connections)、[Signaling](https://developer.mozilla.org/en-US/docs/Web/API/WebRTC_API/Signaling_and_video_calling)。
- 电视必须具备兼容的浏览器、解码器及全屏播放能力。先按实际机型做 WebRTC/H.264/自动播放验证，不能承诺所有智能电视都可用。三星按机型年份列出 Web 引擎能力，LG 也要求按 webOS 引擎版本确认：[Samsung](https://developer.samsung.com/smarttv/develop/specifications/web-engine-specifications.html)、[LG](https://webostv.developer.lge.com/develop/specifications/web-api-and-web-engine)。仅支持 DLNA、没有合适浏览器的电视，仍需要盒子或接收应用。

### 稳定性及安全底线

- 配对码短时有效、确认接收端后投送；会话绑定设备，TLS、短期 TURN 凭据，不开放公网后台管理或采集接口。
- 只传画面、默认无远程键鼠控制；清晰区分连接中、已传流、网络中断，掉线重试有上限且可停止。
- 自适应码率、拥塞控制、关键帧请求、ICE 重启、睡眠/唤醒和网络切换恢复；电视端首帧和持续解码状态回报，不能仅以信令成功称为播放成功。
- 用不同运营商、企业禁 UDP、对称 NAT、TURN/TLS、IP 改变、接收页关闭等隔离用例验收。接收地址不包含后台令牌，配对与媒体会话不跨账户泄漏。

### 成本判断（不是云报价）

- 信令流量很小；主要成本是开发/不同电视适配及 TURN 视频中转。
- 按单路视频 **4 Mbps** 计算：每小时约 **1.8 GB**；**8 Mbps** 为 **3.6 GB/小时**，未计音频及协议开销。100 小时全量中转约 180 / 360 GB；多台电视分别计流量。实际费用由云厂商出网、区域和中继比例决定。
- 纯 P2P 的服务器带宽便宜，但不能拿牺牲连接成功率来省中继。建议先做一台目标电视的接收页＋直连/中转小样，确认兼容和中继比例，再决定产品化。
- **偶尔异网投屏：优先现有第三方工具，选择内容区域捕获。经常跨现场、固定电视且需要一键免安装：再做上述内置 WebRTC。** 本轮不新增云服务依赖、计费项、安装包体积或公网端口。
